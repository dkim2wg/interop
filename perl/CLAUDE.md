# Mail::DKIM2 — Perl implementation of draft-ietf-dkim-dkim2-spec-09

## Project structure

- `lib/Mail/DKIM2.pm` — top-level module: the conventions (CamelCase options,
  snake_case methods, PRINT/CLOSE vs load(), the result/croak error contract,
  string-only exceptions) every module follows. Read it before changing an API.
- `lib/Mail/DKIM2/` — core library modules (see Module map below)
- `lib/Mail/Milter/Authentication/Handler/` — milter integration (DKIM2Sign, DKIM2Verify)
- `t/` — tests (full-chain, interop, body-canon, milter; t/pod.t and
  t/pod-coverage.t require every public method to be documented)
- `tests/emails/` — source test emails
- `tests/expected/` — generated signed test emails (regenerated by t/full-chain.t)
- `bin/` — command-line tools
- `../dns.json` — shared DNS key records for interop testing
- `../keys/` — shared private keys for interop testing
- `../python/` — Python DKIM2 implementation (separate, for interop testing)
- `../spec/` — draft-ietf-dkim-dkim2-spec-09.txt

## Dependencies

The only non-core CPAN dependency for cryptography is CryptX (provides
Crypt::PK::RSA, Crypt::PK::Ed25519, Crypt::Digest::SHA256). Net::DNS does the
public-key lookup. There is no dependency on Mail::DKIM. Recipe computation
uses a built-in capped Myers diff (MessageInstance::_body_diff), the same
algorithm as the C, Python, Go and Mailman generators.

## Header folding rules

Two different canonicalizations are involved, and they treat folding
whitespace differently. Keep them apart.

1. **Header hash** (the `h=` header hash in a Message-Instance; Canon's
   `dkim2_canonicalize_header`): covers ordinary header fields --
   everything except Message-Instance, DKIM2-Signature, X-* and the other
   fields `should_skip` lists. It unfolds and collapses each WSP run to a
   single space. So re-folding at an existing run of whitespace leaves the
   hash alone, but inserting a fold where there was no whitespace adds a
   space and breaks every Message-Instance that hashed that field.

2. **Signing input** (-09 §12.8; Canon's
   `dkim2_canonicalize_sig_header`): covers only the Message-Instance and
   DKIM2-Signature fields. It unfolds and then deletes ALL WSP. Folding these
   two fields -- at creation or later -- cannot change any signature, and
   they are not in any header hash. That makes a fold cryptographically
   invariant, not syntactically valid: the field still has to parse, and
   the grammar allows FWS only in some places (see `fold_header()` below).

### What that means in practice

- **A field we are creating** (a Message-Instance, a DKIM2-Signature): fold
  where the grammar allows FWS -- after a tag's `;`, inside a base64 value,
  beside the `:`s of an `s=` or `h=` item, after a list comma (not in
  `s=`) -- and never inside a Domain, selector,
  algorithm or hash name. Per RFC 5322 §2.1.1 lines SHOULD be at most 78
  characters and MUST be at most 998; we target 72, and a token that cannot
  fold (a long `d=` domain) stays whole on a longer line.
- **An ordinary field we received** (disk, network, previous hop): re-fold
  only at existing whitespace, or not at all -- rule 1.
- **A Message-Instance or DKIM2-Signature we received**: re-folding would not
  break a signature (rule 2), but we still never rewrite one. Keeping their
  bytes as they arrived is a discipline -- byte-stable fixtures, raw fields
  that match what other implementations logged -- not a cryptographic
  requirement.

### Signing input

`Canon::build_signing_input(instances => [...], signatures => [...],
signing => $field)` builds the octets a signature covers from the fields
themselves, whole and as they are in the message, and empties the `s=`
values of the one being signed or checked. The Signer passes the field it
is about to send (`Signature::as_folded_string`, values still empty); the
Verifier passes the field it received. Rule 2 makes folding irrelevant, so
there is one code path and no re-serialisation of a parsed signature.

### Implementation

- `Signature::as_string()` is the unfolded field with its name;
  `Signature::as_folded_string()` the same folded at 72, ready to insert.
- `MessageInstance::as_string()` is the unfolded value WITHOUT the field
  name; `as_header()` is the whole field folded, `as_header_value()` its
  value alone (for a milter's addheader).
- `fold_header()` — folds at `; ` tag boundaries first, then at the latest
  point before the margin that `_dkim2_fold_ok()` accepts (base64 interiors,
  item colons, list commas), else the first one after it; never mid-token.
  Croaks rather than emit a line over 998. Only for headers we are creating.
- Headers read from disk or the network are **never** refolded.

## Module map

- `Chain` — the Message-Instance and DKIM2-Signature fields by number;
  structure errors in the interop contract's order. Verifier, Signer and
  Gate all read the chain through it. Add chain bookkeeping here, not in a
  caller.
- `HeaderPlan` / `BodyPlan` — every instance's header and body hash from
  the message as received, one pass, nothing rebuilt. The Verifier's only
  chain-walk engine. `t/lib/UndoWalkVerifier.pm` is the slow reference the
  tests hold them to (`MessageInstance->undo` and friends).
- `Hop->next_instance` — which instance a hop adds before signing. The
  milter, the DKIM2Sign handler and dkim2sign call it; do not re-derive the
  decision in a front end.
- `Key::signature_algorithm` — the one table of signing algorithms.
- What used to be `Common.pm` (1250 lines) is now five modules by subject:
  `Canon` (what is hashed, canonicalization, signing input), `Fold`
  (`fold_header`), `Address` (paths, domains, relaxed match, Authentic
  From), `Key` (private keys, key records, Domain Policy Records,
  algorithms), `RecipeJSON` (the `r=` JSON). `Common` keeps constants,
  limits, chain numbering, the any/all group combiner and `parse_mime`, and
  imports and re-exports everything that moved, so `Mail::DKIM2::Common::X`
  and `use Mail::DKIM2::Common qw(X)` still work (`t/common-facade.t` pins
  that). New code in `lib/` and `bin/` uses the owning module; a new
  function goes in the module for its subject, not in `Common`.
- `Util` — `check_options`, `is_base64string`. The leaf modules above must
  not `use Mail::DKIM2::Common` (it uses them).
- `MessageInstance->calculate/verify/undo/chain_verifies` still run on
  Email::MIME (with two methods patched into Email::Simple::Header); they
  are the signing side and the reference, not the Verifier's path.

## Consumers

hm vendors a copy of `lib/Mail/DKIM2/` and the two handlers, and can be
patched in the same MR as a refresh. Topicbox-Backend installs from CPAN
and must keep working unchanged: it calls `from_authentic`,
`extract_domain` (deprecated), `Gate->check(AllowNullBodyRecipe => 1)`
(deprecated no-op), `h_digest`/`b_digest`, `parse_mime`, `get_tag('rb')`,
`verify`, `undo`, `chain_verifies` and `calculate`. Result and detail
strings are consumer API: hm reads `$verifier->details` and Gate's
`reason`/`message`.

## MessageInstance::calculate() API

`calculate($current)` — compute MI m=1 for a message with no existing MI.

`calculate($current, $previous, %opts)` — compute diff MI. Hashes are of
`$current` (the newest message). Recipes describe how to reconstruct
`$previous` from `$current`. The `$previous` message must have existing MI
headers. Options (`IgnorePrefixes`, `Algs`, `MaxRecipeLiterals`,
`BodyHash`, `BodyRecipe`) are CamelCase like every other option in the dist;
`verify` and `chain_verifies` take `IgnorePrefixes` too. There is no
process-wide ignore list.

`calculate` never changes the message it is given. (The epilogue options,
which rewrote it and croaked from 0.23, were removed in 0.32.)

## Interop testing

The `t/interop.t` test verifies files generated by the Python implementation
in `../python/tests/expected/`. Both implementations must agree on:

- Header hash computation (header ordering, canonicalization)
- Body hash computation (simple body canonicalization)
- Signing input construction (all MI first, then all DK2, then incomplete sig)
- Signature computation (RSA-SHA256, Ed25519-SHA256)

Known spec ambiguities found during interop testing are documented in
`spec-review-notes.md`.
