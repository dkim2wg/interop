# dkim2.com Landing Page — Design

**Date:** 2026-06-18
**Status:** Approved (pending spec review)
**Author:** brong + Claude

## Goal

Serve a public landing/explainer page at the apex domain `https://dkim2.com`
(and `https://www.dkim2.com`). Today the apex has no vhost or content —
requests fall through to the Mailman vhost, whose certificate only covers
`mailman.dkim2.com`, so `https://dkim2.com` throws a certificate-name
mismatch. This page gives the apex real content **and** its own valid
certificate, fixing that error.

Audience: anyone discovering DKIM2 — a short, skimmable explainer of what
DKIM2 is and why, with links onward to the spec, the working group, the
source, and the live demo services on this host.

## Scope

In scope:
- One static HTML page + one small CSS file, source committed to the repo.
- An nginx vhost for `dkim2.com` + `www.dkim2.com` serving the static root.
- A Let's Encrypt certificate covering both names (via the existing webroot
  renewal mechanism).
- `www` redirects to the apex.

Out of scope (explicitly deferred):
- **Reflector / verify-and-reflect addresses** (see Future Work). Not part
  of this page build, though the page may document them later.
- Multi-page site, CMS, or any build toolchain.
- A `www` DNS record is a manual prerequisite (see Prerequisites), not part
  of the deploy.

## Approach

Plain hand-written static HTML + CSS. No build step, no framework, no
external dependencies. Rationale: the content is one page that changes
rarely; a static file served directly by nginx is the lowest-maintenance
option and matches the demonstration-server nature of the host.

### Source layout (in this repo)

```
deploy/www/
  index.html      # the page
  style.css       # small stylesheet, linked from index.html
```

Deployed to a server webroot, e.g. `/var/www/dkim2.com/`, by copying these
files (documented in deploy/SERVER.md). No server-side processing.

### nginx vhost (`/etc/nginx/sites-available/dkim2.com`)

```
server {
    listen 80;
    server_name dkim2.com www.dkim2.com;
    include snippets/acme-challenge.conf;   # already created for renewals
    location / { return 301 https://dkim2.com$request_uri; }
}

server {
    listen 443 ssl;
    server_name www.dkim2.com;
    ssl_certificate     /etc/letsencrypt/live/dkim2.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/dkim2.com/privkey.pem;
    return 301 https://dkim2.com$request_uri;   # www -> apex
}

server {
    listen 443 ssl default_server;
    server_name dkim2.com;
    ssl_certificate     /etc/letsencrypt/live/dkim2.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/dkim2.com/privkey.pem;
    root /var/www/dkim2.com;
    index index.html;
    location / { try_files $uri $uri/ =404; }
}
```

Making the apex the `default_server` on 443 means bare-IP / unknown-host
hits land on the explainer rather than the Mailman UI.

### Certificate

Issued via webroot (consistent with the renewal fix made 2026-06-18):

```
certbot certonly --webroot -w /var/www/acme \
    -d dkim2.com -d www.dkim2.com --cert-name dkim2.com -n
```

Renews automatically through the existing `certbot.timer` (webroot
authenticator, no nginx downtime).

## Page content

Single page, sections top to bottom. Copy grounded in the DKIM2 spec
abstract and the repo's implementer guide.

1. **Hero** — "DKIM2" wordmark, one-line tagline: each domain that handles a
   message documents it with a verifiable cryptographic signature, forming a
   chain from author to recipient. A small "work in progress — IETF draft"
   badge.

2. **Work in progress** — a clear note that DKIM2 is being developed in the
   IETF **DKIM working group** and is not yet a finished standard. Link:
   https://datatracker.ietf.org/wg/dkim/about/

3. **The problem** — DKIM1 signs once per hop and cannot show whether a
   message was modified between hops; intermediaries (forwarders, mailing
   lists) routinely break signatures.

4. **How DKIM2 works** — the two mechanisms:
   - **Message-Instance (MI) headers** — a hash snapshot of the message at
     each hop, so verifiers can confirm the chain of snapshots is intact.
   - **Chained DKIM2-Signature headers** — each hop signs the current MI and
     all prior signatures, forming a tamper-evident chain.
   Brief mention: also detects unexpected replay and constrains DSNs to
   parties that actually handled the message.

5. **Status & implementations** — this host is a live DKIM2 demonstration
   server; four independent implementations (Python, Perl, Go, C) in the
   project repository interoperate.

6. **Links** —
   - IETF DKIM working group: https://datatracker.ietf.org/wg/dkim/about/
   - DKIM2 spec draft: https://datatracker.ietf.org/doc/draft-ietf-dkim-dkim2-spec/
   - Source repository: https://github.com/dkim2wg/interop
   - Mailman (this host): https://mailman.dkim2.com/
   - Sympa (this host): https://sympa.dkim2.com/sympa
   - (Optional) implementer guide / operator guide from the repo.

7. **Footer** — minimal: project name, "IETF DKIM working group", year.

No hackathon references.

## Prerequisites

- **`www.dkim2.com` A record** — DONE (2026-06-18): resolves to
  `134.209.211.166` from the server's resolver. Required because ACME
  validates `www` during issuance. The apex `dkim2.com` A record already
  existed.

## Styling

Simple, readable, self-contained: system font stack, a constrained
max-width column, generous line-height, a restrained accent color. No web
fonts, no JS. Must be legible on mobile (single-column, responsive
viewport meta).

## Testing / verification

- `nginx -t` passes; reload succeeds.
- `https://dkim2.com/` returns 200 with the page and a valid cert for
  `dkim2.com`.
- `https://www.dkim2.com/` returns 301 to `https://dkim2.com/` with a valid
  cert.
- `curl` of the apex shows no certificate-name mismatch (the original bug).
- `mailman.dkim2.com` and `sympa.dkim2.com` still serve correctly (no
  regression from the new `default_server`).
- All links resolve (2xx/3xx).

## Future Work (not in this build)

**Reflector addresses** on the demo server: a few addresses that verify
incoming mail and forward it back to the sender —
- pass (DKIM2 good, or no DKIM2 but DKIM1/SPF passed) → forward with an added
  DKIM2 signature;
- fail → forward without a signature;
- either way, add a header explaining the validation result.

Tracked separately; the landing page may later document these addresses.
