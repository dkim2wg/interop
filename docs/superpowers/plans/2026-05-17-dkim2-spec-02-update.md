## Summary of spec-02 normative changes

Comparing draft-ietf-dkim-dkim2-spec-01 (2026-04-20) to draft-ietf-dkim-dkim2-spec-02 (2026-05-17):

1. **Version string bump** — everywhere `spec-01` appears (constants + doc strings)
2. **Authentication-Results MUST be excluded from header hash** — New text in §5.2. Currently ALL signing implementations include it; Python mailman already excluded it (its comment was ahead of the spec). **Breaking change**: requires regenerating 3 Python expected emails and 5 Perl expected emails.
3. **Base64 canonical padding clarification** — "padded with zero bits and trailing = characters provided if needed." All libraries already do this; update comments only.
4. **`z` body recipe step removed from JSON schema** — Changelog says "DSNs do not actually need this", but §11 still says MUST for truncated-body DSNs. **Spec inconsistency to raise.** Implementations should keep ignoring `z` if encountered; update comment in MessageInstance.pm.
5. **JSON recipe header-field description as single string** — Schema fix; no wire format change.
6. **JSON keys differing only in case MUST NOT exist** — Moved from schema to prose; already enforced by all implementations.
7. **x-tag ABNF fix** — Extension tag grammar clarified; no behaviour change.
8. **donotmodify semantics clarified** — Explicit text about what "honored" means; no code change to signers.
9. **NEW §10.8: Check donotmodify/donotexplode** — Verifiers SHOULD reject messages where a prior signature's request was violated.

```perl
# Returns (header_hash, body_hash) from a raw MI header line,
# or (undef, undef) if the h= tag is absent or unparseable.
sub _extract_mi_hashes {
    my ($raw) = @_;
    $raw =~ s/^[^:]+://;       # strip "Message-Instance:" field name
    $raw =~ s/\r?\n[ \t]/ /g;  # unfold continuation lines
    if ($raw =~ /\bh=sha256:([A-Za-z0-9+\/=]+):([A-Za-z0-9+\/=]+)/) {
        return ($1, $2);       # (header_hash, body_hash)
    }
    return (undef, undef);
}
```

```markdown
## spec-02: §11 vs JSON schema inconsistency for `z` body recipe step

spec-02 removed the `{"z": true}` body recipe step from the JSON schema
(changelog: "Removed the z body recipe since DSNs do not actually need this")

> "If the message body has been truncated (rather than omitted altogether)
> then in order to allow verification of the DNS contents a Message-Instance
> header field MUST be added to the message with a body recipe containing a
> {"z": true} step."

The `MUST` in §11 and the removed schema entry are contradictory.
Our implementation ignores `z` steps if encountered (backward compat) and
does not generate them (since DSN truncation is not yet implemented).
This inconsistency should be raised with the spec authors.
```
