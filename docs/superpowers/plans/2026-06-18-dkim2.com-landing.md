# dkim2.com Landing Page Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Serve a static landing/explainer page at `https://dkim2.com` (+ `www`), giving the apex domain real content and its own valid TLS certificate (which also fixes the current cert-name mismatch).

**Architecture:** One hand-written `index.html` + `style.css`, committed to the repo under `deploy/www/`, pulled onto the demo server and copied to an nginx webroot. A new nginx vhost serves the apex (as `default_server`) and redirects `www` → apex. A Let's Encrypt cert covering both names is issued via the existing webroot renewal mechanism.

**Tech Stack:** Static HTML5 + CSS (no JS, no build step, no external deps), nginx, certbot (webroot authenticator), Ubuntu/systemd. Deployment over SSH (`ssh dkim2`).

## Global Constraints

- No build toolchain, no JavaScript, no web fonts, no external/CDN dependencies — plain static HTML + one local CSS file.
- No hackathon references anywhere in copy.
- Must include links: IETF DKIM WG (`https://datatracker.ietf.org/wg/dkim/about/`), DKIM2 spec draft (`https://datatracker.ietf.org/doc/draft-ietf-dkim-dkim2-spec/`), repo (`https://github.com/dkim2wg/interop`), Mailman (`https://mailman.dkim2.com/`), Sympa (`https://sympa.dkim2.com/sympa`).
- Responsive/legible on mobile (viewport meta, single-column).
- Server: host alias `dkim2`, IP `134.209.211.166`, webroot for ACME already at `/var/www/acme`, ACME nginx snippet already at `snippets/acme-challenge.conf`.
- Do not break the existing `mailman.dkim2.com` / `sympa.dkim2.com` vhosts.
- Source of truth for the page lives in the repo at `deploy/www/`; the server gets it via `git pull` then copy to `/var/www/dkim2.com/`.

```html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>DKIM2 — verifiable email handling</title>
  <meta name="description" content="DKIM2 lets every domain that handles an email document it with a verifiable cryptographic signature, forming a tamper-evident chain from author to recipient. A work in progress in the IETF DKIM working group.">
  <link rel="stylesheet" href="style.css">
</head>
<body>
  <header class="hero">
    <h1>DKIM2</h1>
    <p class="tagline">Every domain that handles a message documents it with a
      verifiable cryptographic signature — building a tamper-evident chain
      from author to recipient.</p>
    <p class="badge">Work in progress · IETF Internet-Draft</p>
  </header>

  <main>
    <section>
      <h2>Status: a work in progress</h2>
      <p>DKIM2 is being developed in the IETF
        <a href="https://datatracker.ietf.org/wg/dkim/about/">DKIM working
        group</a>. It is an active Internet-Draft, not yet a finished
        standard — details may still change.</p>
    </section>

    <section>
      <h2>The problem with DKIM today</h2>
      <p>DKIM (v1) adds one signature per hop, and each relay can only sign
        what it added. It has no way to show whether a message was modified
        between hops — so ordinary forwarding and mailing lists routinely
        break signatures, and there is no record of who changed what.</p>
    </section>

    <section>
      <h2>How DKIM2 works</h2>
      <p>DKIM2 records the journey of a message with two linked mechanisms:</p>
      <ul>
        <li><strong>Message-Instance (MI) headers</strong> — a hash snapshot
          of the message taken at each hop, so a verifier can confirm the
          chain of snapshots is intact.</li>
        <li><strong>Chained DKIM2-Signature headers</strong> — each hop signs
          the current snapshot <em>and</em> every previous signature, forming
          a tamper-evident chain. Inserting or forging a hop means breaking a
          signature.</li>
      </ul>
      <p>The same chain lets recipients detect unexpected message
        <em>replay</em>, and ensures delivery status notifications only reach
        parties that actually handled the message.</p>
    </section>

    <section>
      <h2>Implementations &amp; demo</h2>
      <p>This host runs a live DKIM2 demonstration server. Four independent
        implementations — in Python, Perl, Go, and C — interoperate in the
        project repository. Two mailing-list managers on this host sign with
        DKIM2 as they forward:</p>
      <ul>
        <li><a href="https://mailman.dkim2.com/">Mailman</a> (this host)</li>
        <li><a href="https://sympa.dkim2.com/sympa">Sympa</a> (this host)</li>
      </ul>
    </section>

    <section>
      <h2>Learn more</h2>
      <ul>
        <li><a href="https://datatracker.ietf.org/wg/dkim/about/">IETF DKIM
          working group</a></li>
        <li><a href="https://datatracker.ietf.org/doc/draft-ietf-dkim-dkim2-spec/">DKIM2
          specification (Internet-Draft)</a></li>
        <li><a href="https://github.com/dkim2wg/interop">Source &amp;
          reference implementations on GitHub</a></li>
      </ul>
    </section>
  </main>

  <footer>
    <p>DKIM2 · developed in the IETF DKIM working group · 2026</p>
  </footer>
</body>
</html>
```

- [ ] **Step 3: Create the nginx vhost (HTTP only first, no cert yet)**

This intermediate version serves ACME on port 80 and serves the page over
**port 80** temporarily, so the cert can be issued before any 443 block
references a not-yet-existing cert path. Run:
```bash
ssh dkim2 'cat > /etc/nginx/sites-available/dkim2.com <<'"'"'EOF'"'"'
server {
    listen 80;
    server_name dkim2.com www.dkim2.com;
    include snippets/acme-challenge.conf;
    root /var/www/dkim2.com;
    index index.html;
    location / { try_files $uri $uri/ =404; }
}
EOF
ln -sf /etc/nginx/sites-available/dkim2.com /etc/nginx/sites-enabled/dkim2.com
nginx -t && systemctl reload nginx && echo RELOADED'
```
Expected: `nginx: ... test is successful` and `RELOADED`.

- [ ] **Step 4: Issue the certificate via webroot**

Run:
```bash
ssh dkim2 'certbot certonly --webroot -w /var/www/acme \
  -d dkim2.com -d www.dkim2.com --cert-name dkim2.com -n \
  --no-random-sleep-on-renew 2>&1 | tail -15'
```
Expected: `Successfully received certificate` and files written to
`/etc/letsencrypt/live/dkim2.com/`.

- [ ] **Step 5: Replace vhost with the final HTTPS version**

Run:
```bash
ssh dkim2 'cat > /etc/nginx/sites-available/dkim2.com <<'"'"'EOF'"'"'
server {
    listen 80;
    server_name dkim2.com www.dkim2.com;
    include snippets/acme-challenge.conf;
    location / { return 301 https://dkim2.com$request_uri; }
}

server {
    listen 443 ssl;
    server_name www.dkim2.com;
    ssl_certificate     /etc/letsencrypt/live/dkim2.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/dkim2.com/privkey.pem;
    return 301 https://dkim2.com$request_uri;
}

server {
    listen 443 ssl default_server;
    server_name dkim2.com;
    ssl_certificate     /etc/letsencrypt/live/dkim2.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/dkim2.com/privkey.pem;
    root /var/www/dkim2.com;
    index index.html;
    location / { try_files $uri $uri/ =404; }
}
EOF
nginx -t && systemctl reload nginx && echo RELOADED'
```
Expected: `test is successful` and `RELOADED`.
