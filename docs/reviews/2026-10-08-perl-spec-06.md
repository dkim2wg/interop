# Perl library adversarial review against spec-06

Reviewed 2026-10-08 at commit `590bc6e2a9bcc316d3c7af4e2acbb1021017fb30`, Mail::DKIM2 0.17. Five independent review lenses: performance, correctness, security, design/readability, and comments/documentation. The local `spec/draft-ietf-dkim-dkim2-spec-06.txt` is the reference. This reviews the implementation, not the working group's decisions or the draft's publication readiness.

The existing suite passes: `prove -lr t` in `perl`, 73 files and 2,219 tests. The initial sandboxed run could not start its milter listener; the full run outside the sandbox passed. New adversarial probes below expose gaps not covered by that suite. No implementation files were changed.

Priorities: P1 warrants prompt attention to availability; P2 is an actionable correctness, API, or documentation defect; P3 is a smaller documentation correction. Findings that overlap between reviews appear once, with their other implications explained.

## Performance review

### R1 — P1: Unsupported signature items cause quadratic CPU and sequential key lookups

Locations: [Verifier.pm:662](../../perl/lib/Mail/DKIM2/Verifier.pm#L662), [Verifier.pm:674](../../perl/lib/Mail/DKIM2/Verifier.pm#L674), [Signature.pm:141](../../perl/lib/Mail/DKIM2/Signature.pm#L141).

A single `s=` list containing distinct selectors and distinct unknown algorithm names reaches the key callback once per item. The verifier looks up keys before checking whether it supports the algorithm. Distinct algorithm names avoid the repeated-algorithm limit. Each accessor reparses the complete list, causing quadratic CPU work. An authentic signature is unnecessary to reach this path. With the default resolver, the calls become sequential TXT queries.

Coordinator reproduction with an immediate `undef` callback: 1,000/2,000/4,000 items took 0.296/1.201/4.750 seconds and caused exactly 1,000/2,000/4,000 callbacks. The independent performance reviewer measured 0.303/1.211/4.867 seconds. Actual DNS latency was not measured. Spec §3.4 says to ignore algorithms that are not implemented.

Parse the list once, reject malformed items, and filter unsupported algorithms before callbacks or DNS. Cache parsed items with invalidation when `s=` changes. Do not simply add an arbitrary item cap that rejects otherwise permitted extensions.

### R2 — P2: Repeated-line bodies make recipe calculation quadratic

Locations: [MessageInstance.pm:497](../../perl/lib/Mail/DKIM2/MessageInstance.pm#L497), [MessageInstance.pm:796](../../perl/lib/Mail/DKIM2/MessageInstance.pm#L796), fallback at [MessageInstance.pm:951](../../perl/lib/Mail/DKIM2/MessageInstance.pm#L951).

Bodies alternating `a,b,a,b,...` versus `b,a,b,a,...` cause expensive repeated-line matching in Algorithm::Diff. `_best_body_diff` runs the complete line diff before considering the flat strategy; `EpilogueThreshold` also computes the diff before deciding to fall back. Coordinator timings for 1,000/2,000/4,000 lines were 0.201/0.853/3.657 seconds for bodies of roughly 3/6/12 KB. This is a signing availability issue for a list processing adversarial content, not a wire-format violation.

Use an explicit diff-work budget and select a literal or epilogue recipe when it would be exceeded. A limit on the resulting recipe size does not limit computation already performed. The measurements exercise the internal diff helper; they do not include the entire MTA path.

## Correctness review

### R3 — P2: Unknown signature algorithms are authenticated as RSA

Location: [Verifier.pm:700](../../perl/lib/Mail/DKIM2/Verifier.pm#L700), dispatch at [Verifier.pm:715](../../perl/lib/Mail/DKIM2/Verifier.pm#L715).

The verifier selects Ed25519 by a prefix match and otherwise uses RSA-SHA256. A message correctly signed with an RSA fixture key but declaring `future-alg` returns `pass`. This reports successful verification under an algorithm that the implementation does not support, contrary to §3.4. It also shares the missing algorithm filter responsible for R1. Match implemented names exactly and validate the selected key's algorithm. This does not show that an attacker can forge a known algorithm's signature without its key.

### R4 — P2: Valid uppercase Message-Instance tag identifiers fail

Locations: [MessageInstance.pm:303](../../perl/lib/Mail/DKIM2/MessageInstance.pm#L303), [Common.pm:413](../../perl/lib/Mail/DKIM2/Common.pm#L413).

§7 explicitly makes tag identifiers case insignificant. MI parsing retains their case and then checks lowercase keys; version extraction recognizes lowercase `m` only. A correctly signed `H=` instance fails with “no supported hash algorithm.” A correctly signed `M=` instance is omitted from the signing input and fails signature verification. Normalize identifiers consistently during both extraction and parsing. Although some numeric ABNF terminals spell lowercase, the explicit §7 prose requires case-insensitive treatment.

### R5 — P2: Duplicate Message-Instance tags are silently overwritten

Location: [MessageInstance.pm:305](../../perl/lib/Mail/DKIM2/MessageInstance.pm#L305).

§7 requires one tag of each kind. A signed MI containing an incorrect `h=` followed by a correct `h=` passes, because hash assignment silently replaces the first value. Detect duplicate identifiers case-insensitively before storing any value. Signature tag parsing already has a duplicate check; the separate MI parser lacks it.

### R6 — P2: Malformed timestamps bypass freshness checks

Location: [Verifier.pm:609](../../perl/lib/Mail/DKIM2/Verifier.pm#L609).

A correctly signed `t=garbage` message passes with timestamp checking enabled. Numeric coercion emits a warning, evaluates the value as zero, and skips the age policy. §8.4 requires ASCII decimal `1*DIGIT`; §11.2 requires format validation. Validate syntax independently of `SkipTimestampCheck`, then apply the age policy. This requires a signed malformed timestamp; it does not allow editing an existing signed timestamp without invalidating the signature.

## Security review

### R7 — P2: Multiple DNS key records are accepted

Location: [Verifier.pm:857](../../perl/lib/Mail/DKIM2/Verifier.pm#L857).

`fetch_public_key` returns the first TXT answer without considering the others. A mock answer containing a valid key and a revoked-key TXT record returns a usable key. §11.5 expressly requires an error for multiple returned records. The security reviewer also tested the default fetch path on an existing signed fixture and obtained `pass`. Validate record cardinality before selecting a key, while preserving the distinction between multiple records and multiple character strings within one TXT RR. This is ambiguous-key acceptance, not evidence of arbitrary DNS forgery.

### R8 — P2: DNS key record validation is incomplete

Location: [Common.pm:561](../../perl/lib/Mail/DKIM2/Common.pm#L561).

The parser searches for `k=` and a nonempty `p=` with regexes, handles only `ed25519` specially, and defaults other key types to RSA. Changing a fixture from `k=rsa` to `k=unknown` still yields an RSA key, independently reproduced by the coordinator. The security reviewer additionally obtained `pass` with `v=garbage`, and with a single TXT record containing `p=;` before another valid `p=`: the regex skips the empty value and finds the later key.

§11.5 requires validating key records and prohibits using malformed ones; §8.9 requires algorithm matching. Parse the complete key record, reject duplicates, honor an empty `p=` as revoked, validate explicit version/key types, and enforce the signature/key algorithm relationship. Absence of `k=` legitimately defaults to RSA; an explicit unsupported `k=` must not.

### Security/design concern: unsigned DSN compatibility needs an explicit propagation policy

Locations: [DSN.pm:334](../../perl/lib/Mail/DKIM2/DSN.pm#L334), [DSN.pm:367](../../perl/lib/Mail/DKIM2/DSN.pm#L367).

`authenticate` deliberately allows `dsn_result=none` when the enclosed message chain verifies, and `propagate` trusts its `ok`. Thus `ok` authenticates the enclosed message in this case, not the unsigned delivery status. The caller's own-hop check is explicitly delegated to the caller; `ForwarderDomain` is required by `propagate` but is not used to validate or select the removed hop.

This is a policy/design concern rather than a confirmed violation of §12.1.2, whose opening condition concerns DKIM2-signed DSNs. Prefer an explicit opt-in for legacy unsigned DSN propagation, distinct statuses for original-message verification and DSN authentication, and an enforceable own-hop precondition. A caller must not interpret `ok` alone as proof of a genuine signed bounce or a bounce about its own forwarding activity.

## Design and code legibility review

### R9 — P2: Public option validation is inconsistent

Locations: [Signature.pm:21](../../perl/lib/Mail/DKIM2/Signature.pm#L21), [MessageInstance.pm:833](../../perl/lib/Mail/DKIM2/MessageInstance.pm#L833), promised contract at [DKIM2.pm:130](../../perl/lib/Mail/DKIM2.pm#L130).

`Signature->new(Domian => 'example.com')` succeeds with an undefined domain. `MessageInstance->calculate($message, undef, Algz => ['sha512'])` succeeds and computes SHA-256. HeaderParser constructors reject unknown options, but other public entry points silently ignore them despite the distribution's advertised convention. This hides configuration mistakes, including algorithm-selection mistakes.

Introduce a shared validator with an explicit allowed-option set per public constructor/class method. Keep protocol parsing, caller configuration errors, and verification outcomes separate. This is an API-contract defect, not a spec requirement to use a particular internal architecture.

### Design recommendation: remove or reset instance parsing

Location: [TagValueList.pm:17](../../perl/lib/Mail/DKIM2/TagValueList.pm#L17).

The implementation supports parsing into an existing object but does not clear old tags or the duplicate flag. Parsing `i=1; m=1; d=old.example`, then `i=2; m=2`, leaves `domain()` equal to `old.example` while serialization omits `d=`. The documented API presents `parse` as a constructor, so this is not counted as a promised-API defect. Either reject instance calls or reset all parsing state.

The separation of Gate from Signer, bounded chain numbering, and shared parser base are useful design choices. The parser discrepancies in R4/R5/R8 show where further consolidation would prevent semantic drift. Prefer shared parsed representations and validation routines over comments asserting that duplicated implementations agree.

## Human-friendly comments and documentation review

### R10 — P2: README signing example silently produces nothing

Location: [README:51](../../perl/README#L51).

The example passes a fresh message directly to Signer without creating a Message-Instance. Signer returns `fail (no Message-Instance field to sign over)`, and the conditional print hides the failure. Add originating-hop MI creation, handle signing failure explicitly, and show inserting the signature into the outgoing message. If the example assumes a preprepared message, say so and link to its preparation.

### R11 — P2: Module round-trip synopsis verifies the unsigned intermediate state

Location: [DKIM2.pm:41](../../perl/lib/Mail/DKIM2.pm#L41).

The synopsis saves the generated header but does not prepend it before verifying `$message`. The demonstrated result is `permerror (PERMERROR Message-Instance m=1 is not signed)`, not the documented `pass`. Insert `$header . "\r\n"` before the message and describe a one-hop pass. Both R10 and R11 were reproduced by the coordinator.

### R12 — P2: Contributor folding guidance conflates two canonicalizations

Location: [CLAUDE.md:63](../../perl/CLAUDE.md#L63), implementation at [Common.pm:207](../../perl/lib/Mail/DKIM2/Common.pm#L207).

The contributor guide says signing canonicalization collapses whitespace and that later signatures depend on the prior signature's raw fold bytes. §9.6 and the implementation delete all WSP in MI/DK2 signing headers. Valid changes to folding whitespace therefore leave their signing canonical form unchanged. Ordinary message-header hash canonicalization has different rules.

Explain these as separate operations. If preserving folds is a useful implementation discipline, label it as such instead of a cryptographic requirement. This matters because the guide strongly instructs future maintainers how to make changes.

### R13 — P3: Byte-preserving serialization claims are inaccurate

Locations: [TagValueList.pm:24](../../perl/lib/Mail/DKIM2/TagValueList.pm#L24), [TagValueList.pm:92](../../perl/lib/Mail/DKIM2/TagValueList.pm#L92), [Signature.pm:449](../../perl/lib/Mail/DKIM2/Signature.pm#L449).

Parsing `I = 1 ;\tD=example.com;` serializes as `I=1; D=example.com`. Case and order survive; separator whitespace and trailing delimiters do not. Replace “byte for byte” with a precise description of what is preserved. §9.6 whitespace removal makes this normalization harmless for ordinary signing input; the defect is the explanation, not demonstrated signature failure.

### R14 — P3: FWS comment overstates permissible whitespace

Location: [Signature.pm:117](../../perl/lib/Mail/DKIM2/Signature.pm#L117).

The comment claims §2.12 permits FWS anywhere inside every tag value. §2.12 defines whitespace, while §2.13 permits internal FWS in base64strings; individual tag productions constrain its placement elsewhere. Explain base64 folding and list delimiters specifically, and distinguish permissive whitespace removal from syntax validation. Do not teach maintainers that arbitrary folds inside domains or decimal digits are necessarily legal.

### R15 — P2: DSN examples advertise unavailable DNS configuration behavior

Locations: [DSN.pm:475](../../perl/lib/Mail/DKIM2/DSN.pm#L475), [DSN.pm:522](../../perl/lib/Mail/DKIM2/DSN.pm#L522), implementation at [DSN.pm:304](../../perl/lib/Mail/DKIM2/DSN.pm#L304).

The synopsis says `PubkeyCallback` can be omitted to use DNS, but `authenticate` immediately croaks when it is absent. Its POD also says `Resolver` is passed to the verifiers, yet the method neither reads nor forwards that option. Coordinator reproduction without a callback returns `authenticate: need PubkeyCallback`. Implement the advertised standard DNS path and Resolver forwarding, or document the actual required callback and remove the unsupported option claim.

### R16 — P2: Distribution-wide exception promise has undocumented exceptions

Locations: [DKIM2.pm:164](../../perl/lib/Mail/DKIM2.pm#L164), [Validate.pm:180](../../perl/lib/Mail/DKIM2/Validate.pm#L180), [Validate.pm:403](../../perl/lib/Mail/DKIM2/Validate.pm#L403), intentional narrower scope at [Common.pm:550](../../perl/lib/Mail/DKIM2/Common.pm#L550).

The top-level conventions say any reference exception passes through every library `eval` to the host. Validate catches and suppresses such exceptions. A callback throwing a blessed `Host::Timeout` on a signed fixture returns a report with `overall=none` and is called twice, so work continues after the first exception. Common's internal comment explicitly exempts the demo/validator modules; the user-facing contract does not.

Either propagate foreign exceptions consistently or clearly scope the promise to the core signing/verifying path and define report behavior on interruption. This reproduction demonstrates a misleading contract and continued work; it does not establish that a production MTA's timeout is bypassed, since the core Verifier correctly propagates these exceptions.

## Reproduction and follow-up

The sibling `perl-spec-06-correctness-probes.pl` reproduces the baseline pass, uppercase MI failures, duplicate MI acceptance, unknown signature algorithm acceptance, malformed timestamp acceptance, multiple DNS record acceptance, and unknown key-type acceptance using local fixtures. Run it from any directory with the repository root as its first argument:

```sh
perl docs/reviews/perl-spec-06-correctness-probes.pl /absolute/path/to/interop
```

The performance probes can be reproduced from the repository root:

```sh
perl -Iperl/lib -MMail::DKIM2::Verifier -MTime::HiRes=time -MMIME::Base64=encode_base64 -e 'for my $n (1000,2000,4000) {my $q=0;my $s="DKIM2-Signature: i=1;m=1;t=1;d=example.com;mf=".encode_base64("<a\@example.com>","").";rt=".encode_base64("<b\@example.com>","").";s=".join(",",map {"sel$_:unknown$_:AA=="}1..$n).";\r\n\r\n";my $t=time;my $v=Mail::DKIM2::Verifier->new(SkipTimestampCheck=>1,PubkeyCallback=>sub{$q++;return undef})->load($s);printf "%d %.3f calls=%d result=%s\n",$n,time-$t,$q,$v->result}'

perl -Iperl/lib -MMail::DKIM2::MessageInstance -MTime::HiRes=time -e 'for my $n (1000,2000,4000) {my $a=join("\r\n",("a","b")x($n/2));my $b=join("\r\n",("b","a")x($n/2));my $t=time;Mail::DKIM2::MessageInstance::_best_body_diff($a,$b);printf "%d %.3f\n",$n,time-$t}'
```

Prioritize R1/R3 together, then complete DNS key validation (R7/R8), MI syntax validation (R4/R5), timestamp validation (R6), and a bounded recipe strategy (R2). Correct the examples and API contracts in the same review cycle. Add regression tests for the demonstrated cases, including the difference between unknown algorithms and malformed known algorithms, TXT strings versus TXT records, and timestamp syntax versus timestamp age.

Coverage limits: no external DNS load test, fuzzing campaign, memory-limit stress test, deployed MTA audit, or cryptographic primitive audit. Measurements are local and small; larger-scale effects are extrapolation. Existing chain-number and field-count limits are useful, and copy-range validation prevents repeated overlapping reconstruction. These findings are not an exhaustive security certification.
